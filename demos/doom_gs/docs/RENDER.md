## 1. The native level and render tables

### 1.1 Principles

1. **Records the front end reads from RamWorks are arrays of records**
   with a power-of-two stride or a stride of 24, fetched whole into zero
   page or main memory by one `FAR_GET`. A PSRAM line is 8 bytes and a
   miss costs about 131 clocks on F1.2.1 [R `tools/a2vm/README.md:668`];
   byte planes would cost a miss per field.
2. **Arrays the front end indexes by column live in fast memory as byte
   planes**, X = column 0-159, as `MEMORY_MAP.md` 3.3 already has them.
3. **Indexes are bytes where the counts allow**: sectors (at most 250 in
   E1 [M: levels]; `$FF` means none, as upstream's `NO_INDEX8`
   [R `r_wall65.s:531-535`]), textures (DOOM1's texture numbers are below
   256; the converter checks), drawsegs (128). Nodes, segs, sides, lines,
   subsectors and vertices are 16-bit.
4. **Values are upstream's, bit for bit.** A field may be narrowed only
   when the converter proves every value fits (a light level in a byte), and
   a narrowed field is widened back exactly by the code that reads it.
5. **Upstream's derived address tables go** (`CORE_LN36`, `CORE_SEC58`,
   `CORE_NODEADR` in bank `$21` [R `r_wall65.s:42-43`, `r_bsp65.s:50`]):
   an index times a power of two replaces them.
6. **Nothing in the render phase reads the level through a pointer table
   per column.** The texel address of a wall column is computed from the
   texture directory (1.4).

`LVMAP` holds 35,845 B at most [A on M: levels], `LVSEG` 44,688 B: both fit
the 48,640 B of `$0200-$BFFF`.

**Static and dynamic fields.** Segs, nodes, subsectors and the pegs are
constant for a level. Sector heights, pics and lights, side textures and
offsets change in play (doors, lifts, switches, lights, scrollers) and are
written by game logic; `validcount` by both game logic and the renderer
[R `r_frame65.s:285`, `r_bsp65.s:732-737`]. In milestone 7 the harness
writes the dynamic fields every frame (section 2); milestone 10's game logic
will keep them in this layout, or the owner of that milestone changes the
layout here and in the converter together.

**The vertex angle cache.** Upstream caches `R_PointToAngle16` of each seg
vertex while the view's map unit stays [R `r_bsp65.s:12-15`, `:106-128`].
`pointAngle` reads only the map units of the point and of the view
[R `r_iigs65.s:45-60`; MATH: `pta16p` takes 16-bit x, y, viewx, viewy], so
the cache never changes a result; its state is not compared. It does
change the cost: standing still, upstream computes no vertex angle at all
(0 `vtxAngle` calls [M: calls, appendix B]), and each one costs about 19
µs natively [M: MATH]. So the native cache follows upstream's rule
exactly [R `r_bsp65.s:106-128`]: at `nr_bsp` entry, when the view's map
unit (`viewx`, `viewy` bits 16-31) differs from `VA_VX`, `VA_VY`, or the
stamp is 0, it stores the map unit and advances the one-byte stamp; when
the stamp wraps from 255 it clears every vertex stamp (1,207 B) and starts
again at 1. An entry is valid when its stamp equals the current one. The
stamp does **not** change each frame. Upstream numbers vertices by a hash
of (x, y) at level load, one number for each distinct point
[R `i_viigs65.s:1900-2000`, `memmap.inc:93`]; the converter numbers the
distinct end points itself, which is the same numbering up to renaming,
so with the cache injected from upstream's (2.3) the native walk computes
a vertex angle exactly when upstream calls `vtxAngle`. Frame mode checks
that count (4.3), which makes the cache's behaviour observable although
its contents are not compared.

### 1.4 Textures and texels

**One slot per texture column.** Upstream's record carries a 24-bit texel
pointer, the post data of a patch column or of a composed column
[R `lists.inc:41-51`; `research/iigs-renderer.md` 2.10], and the row
blocks read up to 127 bytes past it, wrapping the texel index with `and
#$7f` [R `research/iigs-renderer.md` 2.10; `src/native/README.md`: M5 "The
stage"]. So the texels a record can show are exactly the 128 bytes that
follow its pointer in upstream's memory, whatever lies there. The
converter copies, for each column c of each texture t, those 128 bytes into
a 128-byte slot:

    slot(t, c) = TXBASE[t] + 128 * (c & TXWM[t])     in RamWorks bank TXBANK[t]

A texture is at most 256 columns wide (widthmask + 1 ≤ 256 [R `r_seg65.s:
305-330`: the mask is a byte]), so it needs at most 32 KB and never crosses
a bank. A record's native `R_SRC` is (low, high, bank) of the slot, the
format milestone 5's replay already reads [R M5 "The record layout"]. The
texel source costs a 16-bit add per tier record instead of upstream's
column-table read.

| Table | Size | Content | Where |
| --- | ---: | --- | --- |
| `TXBANK`, `TXLO`, `TXHI` | 3 × 256 | Bank and address of slot 0 of each texture (by upstream texture number). Bit 7 of `TXBANK` (RamWorks banks are 0-127) flags a texture with patchless columns (`TXFLAT`) | W, per level (1.7) |
| `TXWM` | 256 | Widthmask; 0 with `TXBANK` 0: no columns | W, per level |
| `TXHT` | 256 | `textureheight` in map units, for `rowMod` [R `r_wall65.s:1564-1590`]; the converter checks every value is below 256 | W, per level |
| `TXFLAT` | per flagged texture | Columns with no patch (upstream's entry with 1 in the top byte [R `r_seg65.s:1509`]): a bitmap of the texture's columns in `LVMAP`, read only when bit 7 of `TXBANK` is set; `TXWM` bit layout unchanged | `LVMAP` |
| Slots | 128 per column | The 128 bytes after upstream's texel pointer | `TEX0`.. banks |
| Sky slots | 256 × 128 = 32,768 | The 128 bytes after `skypatch + columnofs[c] + 3` for c = 0-255 (`skywidthmask` 255 in DOOM1 [A; the converter reads `skywidthmask`, `r_data65.s:69`, `:202`]) | one texel bank |

Which textures: every texture whose `COLDIR` entry is made in the
reference state the converter reads, which covers the sides' textures at
the level's start [M: levels]. Nothing else can be converted from that
state: the other textures have no columns in it. Upstream makes the
switch partners and the slime frames at the load only while column
memory stays within `MORE_BANKS` [R `w_level65.s:520-560`], and makes any
other texture in the middle of a frame when a wall first shows it
(`tierMake` calls `needColumns`, which calls `R_MakeTextureColumns` for a
texture without columns [R `r_seg65.s:505-516`, `:3410-3419`]). New
columns are appended at `colmem`, which also changes the over-read bytes
(1.10) of the slots whose 128 bytes reached the end of column memory.

So a level has **conversions**, not one conversion. `rendercap.py`'s
first pass marks every `R_MakeTextureColumns` call after the level's first
frame (4.1); its second pass takes a full RAM dump at the next
`R_FillStamps` entry after each such call, and `levelconv.py` converts it
again (a new level key, since the source hashes change). A frame uses the
conversion of the last full dump at or before it. A frame whose records
hold an `R_SRC` that no slot of its conversion maps is a failure of the
capture, not a case to skip. `levelconv.py` lists the **open-ended
slots**, those whose 128 bytes reach the end of `colmem`, and reports which
of them changed between two conversions of a level. The game's converter
(milestone 9) must make every texture a level can show at the load.

**Memory.** E1M2's 5,416 columns take 693,248 B [A on M: levels], about 15
banks of 48,640 B with the animations and the sky; the converter packs
textures first-fit into banks and reports the count per map.

**The texel map.** Upstream's texel pointers are not unique per (texture,
column): a patch column can serve several textures. The converter writes,
per level, the map from each slot to the upstream address it copied from,
so that the comparison maps a native `R_SRC` back to upstream's (section
4.3), and it checks every slot's 128 bytes against the reference's RAM.

### 1.10 `tools/native/levelconv.py`

**Input:** a memory image of the reference (a ref816 image, a `--dump-ram`
file or a `--dump-at` stream record) holding a level, and the link map.
**Output**, in `build/native/render/levels/MAPHASH/`:

| File | Content |
| --- | --- |
| `level.img` | `A2VMIMG1` records: `LVSEG`, `LVMAP`, `TEX0`.. banks; the W per-level tables as a separate record set (the render window image includes them, section 3.4) |
| `level.json` | Format `render-level 1`: the map, counts, each array's bank, base and stride, each texture's bank, base, widthmask and height, the sky's slots, `skyflatnum`, `skywidthmask`, the texture numbers converted, the BSP depth, banks used, and the SHA-256 of every source range |
| `texmap.json` | Each slot's upstream source address (1.4) |

It reads upstream's objects with the bridge (`tools/bridge/upstream.py`
`Reader`: sectors, lines, sides, subsectors, segs, nodes by identity), and
upstream's renderer tables by symbol (`COLDIR` `$25:0000`, the column
tables, `FLATCM`, `textureheight`, `texturetranslation`, `skypatch`'s lump,
`skywidthmask`, `skyflatnum`, `numnodes`), never by a guessed address.

**Checks** (each a failure, never a warning):

- every count within its native limit (sectors below 255, textures below
  256, heights below 256, BSP depth at most 20, each array inside its bank);
- decode of the native level through `rlayout.py` gives back upstream's
  canonical objects for every rendered field;
- every slot's 128 bytes equal the reference's RAM at its source; every
  made texture column has a slot; the open-ended slots (1.4) listed;
- `skypatchnum` names a lump of the WAD directory (0.1);
- the static fields equal across two dumps of the same level load (the
  bridge's "Level tables" check [R `tools/bridge/README.md:341`]).

**The contract with milestone 9.** `render-level 1` is the layout, not the
converter: milestone 9's WAD loader must produce the same bytes. One part is
hard to reproduce from the WAD alone: a slot holds the 128 bytes after the
texel pointer, which for a post shorter than 128 texels include whatever
upstream's level image placed after it (`OVERREAD 128`
[R `research/iigs-renderer.md` 2.10]). Section 6, risk 6.

### 2.3 How the harness injects it

`tools/native/framestate.py` builds one frame's a2vm input from:

1. the reference state at `R_FillStamps` entry (a `--dump-at` record,
   section 4.1), read by symbol (2.1, 2.2). Most of these dumps are
   partial, and `upstream.Reader.read` cannot take them: it locates and
   checks every game-state region, the level window (nodes `$33:0000`,
   segs `$34:5351` in the demo), bank `$21`, the flood and sight tables
   among them [R `tools/bridge/upstream.py:267-340`,
   `tools/bridge/schema.py` `regions`], and a bank missing from the dump
   reads as zero [R `tools/bridge/memory.py:91-101`]. So `framestate.py`
   reads the render fields directly: the tables' bases and counts by
   symbol (`_g_sectors`, `_g_sides`, `_g_lines`, `texturetranslation`,
   `textureheight`, the player and its `mo`), each field at its
   `offsets.inc` offset through the bridge's `Schema` constants, from the
   zone banks `$06-$09` that every P0 dump holds. On each level's first
   frame, whose P0 is a full dump, it also runs `Reader.read` and requires
   0 problems and the same render fields from both reads, which checks the
   direct reader. (Overlaying a partial dump on the level's first full
   dump would pair this frame's zone with another moment's flood, sight
   and guard tables, which the Reader's consistency checks were not built
   for.)
2. the level of that state from `levelconv.py` (built once per level and
   cached by the SHA-256 of its source ranges);
3. **the weapon-clip seam:** the reference state just after `jsr
   weaponClip` returns inside `weaponClipSame` (`r_frame65.s:893`; the pc
   is `weaponClipSame + 3`): `floorclip`'s low bytes, `FR_VIS` (42 B) and
   `MM_WPOK` [R `r_frame65.s:892-943`, `r_sprite65.s:799-802`]. The
   harness build's `wclip_pass` (a card routine in the test driver, not
   game code) copies them from the `SEAM` bank into `FLOORCLIP`, the frame
   block and `FRVIS` (`$0CA0`), where the native weapon-skip bookkeeping (stage C)
   compares `FRVIS` with `WPREV` byte for byte as upstream does
   [R `r_frame65.s:913-921`]. Milestone 8 replaces the stub with the clip
   pass.

It writes `A2VMIMG1` records: the frame block, the dynamic fields into
`LVMAP` (heights, pics, lights, `validcount` stamps, side textures and
offsets), `TEXTRANS`, `LNMAP`, the fill spans, the weapon skip, the native
vertex cache from upstream's (the frame block's `VA_VX`, `VA_VY` from
upstream's, the stamp 1 when upstream's `VA_FRAME` is not 0 and 0
otherwise, and stamp 1 with its angle on each vertex whose `MM_SEGSTAMP`
equals `VA_FRAME` [R `r_bsp65.s:106-128`, `:798-805`]), and the
colormaps. Every byte of the
machine it does not define is filled with `$A5` or `$5A` (as milestone 5
[R M5 "Verification"]).

**Why not the bridge's port writer.** Its manifest describes byte planes
with a stride of 1 [R `tools/bridge/README.md:287-289`]; the render
layout's records have strides of 4 to 32. Stage A adds an optional
`stride` to the manifest format (`tools/bridge/layout.py`, default 1, the
existing manifests unchanged) and makes `levelconv.py` write the sector
and side render fields as a `bridge-port-layout` manifest, so that
`bridge.py from-port` can read them back and milestone 10 inherits one
layout. The encoder itself is `rlayout.py`'s, used by both tools.
(Correction, stage A: the lines' render field is `LNMAP`, one bit a line,
which the manifest's byte-plane encodings cannot describe; the manifest
has the sectors and sides, their counts at `LVCOUNT` `$03A0`.)

windows run from W: RAMWRT does not move fetches, and `ALTZP` swaps the
card itself away.

$C08B` twice back to bank 1), `STA $C008`, `CLI`. No zero-page or stack
access inside [R `MEMORY_MAP.md` rule 7]. Two soft-switch writes a lookup,
five with bank 2 [A], about 2 and 5 µs [A on M: 0.95-0.98 µs a switch,
`memory` 1.2].

### 3.6 Records and drawsegs

**Staged record** (aux 0 `$A000-$BFFF`, then `RECSP`): upstream's record
with the column after the kind: `kind, column, R_ROW, R_END, ...`, so a
`K_TEX` is 12 bytes and a `K_FILL` 6 [R `lists.inc:32-72`; A]. Fields keep
upstream's meaning: `R_TF`, `R_TI`, `R_SF`, `R_SI` the position one row
before the first and the step, both halved [R `lists.inc:41-49`], `R_CMP`
upstream's page byte, `K_FILL`'s `R_B1` the byte of the first row's parity
[R `r_seg65.s:1668-1685`], `R_SRC` the native slot (1.4). The replay of
milestone 5 reads the same fields packed by column [R M5 "The record
layout"]; the per-column packing is milestone 8's (it runs after the masked
phase adds its records).

**How many records a frame makes has no fixed bound.** Upstream's lists
hold at most 53,760 B at once [R `research/iigs-renderer.md` 2.7,
`lists.inc:6-17`], but when no extra page is left `newPage` draws all
lists early (`flush`) and starts them again [R `r_list65.s:272-323`], so a
frame's records, flushed and final together, can exceed it. The native
front end never flushes early: it stages the whole frame. So:

- `rendercap.py` measures, for every captured frame, the bytes of the
  records upstream made (every P2 flush and the P3 lists, plus a column
  byte a record) and reports the largest per set;
- `rlayout.py` sizes `RECSP` to hold the largest measured frame plus half
  again, at least two banks (aux 0 and two spill banks hold 105 KB);
- when staging and spill are full, `rec_flush` stops the frame: the
  status byte of the frame block names the overflow and every build
  (there is no other before milestone 8) executes `BRK` with its code, so
  the harness fails the frame. Nothing is dropped silently. What the game does instead (an early replay, as
  upstream's `flush`, or more banks) is milestone 8's decision, with the
  replay.

**Drawseg** (`RENDB`, 32 B): seg (2), x1, x2 (1 each), scale1, scale2,
scalestep (4 each), silhouette (1), bsilheight, tsilheight (4 each),
sprtopclip, sprbottomclip (2 each: the opening index minus x1, or `$7FFF`
`screenheightarray`, `$7FFE` `negonearray`), maskedtexturecol (2: the
opening index minus x1, or `$8000` null) [R `offsets.inc:25-38`,
`r_wall65.s:1499-1529`]. `DSX1`/`DSX2` and the count in main.
(Correction, stage B: the design had `$FFFF` and `$FFFE` for the two
arrays, which an index minus x1 of -1 or -2 would be; an index minus x1
lies in -160 .. 2,560.)

**Openings:** the opening index space is upstream's (2,560 entries,
`lastopening` an index [R `r_state65.s:16`, `:34-35`]). Low bytes in aux
0 `$0C00` [R `MEMORY_MAP.md` 5]; high bytes, needed only by masked texture
columns (clips are below 256), in `OPENHI` (`RENDB`), written with one
`FAR_PUT` after the seg from the W buffer.

### 3.9 Rules of our own, and the frame's stops (added in verification)

A column seen from behind happens in a legal view: when a wall is seen
at a grazing angle, the centre angle of its first or last column can lie
just past the seg's end, where `angleb` (= ANG90 + the column's angle -
`rw_normalangle`, also the texture angle `rw_centerangle` +
`xtoviewangle[x]`) is ANG180 or more. Upstream then leaves its tables:
`R_ScaleFromGlobalAngle`'s `sineLow` reads with a negative index, which
crosses into bank 3 and reads upstream's own code, one word of it patched
per seg (`c17Return`) [R `r_iigs65.s:535-542`], and `tcExact`'s `long:`
read goes past `finetangent` part 4 into live data (`openings`) [R
`r_seg65.s:2017-2077`]. Neither can be reproduced without shipping
upstream's code bytes and live memory, so no build can equal upstream on
such a frame, lockstep build included. Stage B stopped the frame there
(`ST_SINE`, `ST_TANGENT`, `BRK` in every build); the game would have
stopped on a legal view. The native code now takes a rule of its own,
sets its bit in the frame block's `RULES`, and goes on:

| Rule | Where | The value | Why |
| --- | --- | --- | --- |
| `RULE_SINE` (1) | `rwall.s` `rsga`: `angleb` ≥ ANG180 (its high word's bit 15) | The scale 256 | Vanilla DOOM's result: a negative `sineb` makes `num` negative over a positive `den`, which `R_ScaleFromGlobalAngle` clamps to 256 (and `FixedDiv`'s overflow case gives the same). The column is drawn 1/256 of its height in map units (a 256-unit wall: one pixel) |
| `RULE_TANGENT` (2) | `rseg.s` `tcexact`: the texture angle ≥ 4096 | The table's end: 4095 below 6144 (the angle just past ANG180), 0 from 6144 (just below 0); both read part 4 [1023], with the sign of their side | The nearest angle in the table; the value stays among those the table already gives, so nothing downstream sees a new range |

`anglea` = ANG90 + `xtoviewangle[x]` lies in `$2000-$6000` for every
column, so the other sine never needs a rule (`rtables.py` checks the
table, and so does `tests/test_native_render.py`); `sinelow` shifts
logically.

**How the harness treats them.** A run whose `RULES` is not 0 reports
`rules N: a rule of our own ran` as a problem (frame mode, checkpoint A,
routine mode), so no captured or synthetic frame can take a rule
unnoticed; none does (acceptance 1: 188 frames, `RULES` 0). The
synthetic cases where upstream leaves its tables (`routinesynth.py`:
`negsine`, the whole wall behind; `grazefirst`, `grazelast`, only the
first or last column, both rules and both branches of the tangent rule)
are `render_check.RULED`: each must take exactly its rules and equal
upstream wherever upstream stays in its tables (`ruled_diff`): a wall's
drawseg field by field, the scale of a ruled end the rule's 256 and the
step between the ends scaleSlow's; a seg loop call (from upstream's
scales) every output, the records of the columns within 8 of the ruled
one left out (their texture u is interpolated from the ruled column's).
The tangent rule's value itself is checked by construction only (the
two ends' records are left out); planted bugs show a wrong sine value, a
missing flag and a tangent rule taken inside the table caught.

**The stops that remain** (`STATUS`, `BRK` in every build): `ST_DEPTH`
(the node frames are full) and `ST_TEXTURE` (a texture without slots)
cannot happen on a level `levelconv.py` accepts (it refuses a deeper BSP
and converts every texture the level source made); `ST_RECORDS` (the
staging and the spill are full) is milestone 8's decision (3.6, risk 14).

**The owner's answer** (2026-09-30, `NATIVE.md` 15 question 13: "treat
it as a known difference"): on a grazing frame the native game renders
by these rules, and upstream renders from its own code bytes, so such a
frame differs from `ref816` in lockstep-schedule mode (`NATIVE.md` 15.1
row 4) whatever the port does. It is a known divergence, as the
`validcount` fix is: the lockstep comparison skips a frame whose `RULES`
is not 0 and reports it by name, never as a pass. No captured frame
reaches it (acceptance 1: 188 frames), so its frequency in play is
unknown.

### 4.2 Native runs

`render_check.py` builds the harness (`make -C src/native -f render.mk`),
then for each case an a2vm image: the level (`level.img`), the tables
(`rtables.py`), the frame (`framestate.py`) or the routine state, the code,
the driver; every other byte `$A5` in one run and `$5A` in the other [R M5
"Verification"]. a2vm runs with `--core w65c02s`, a cycle limit, snapshots
of the needed ranges before and after the call (`--snapshot-ranges`),
the write log (below), `--lowest-s-in` over the code, `--irq-bounds`
with a live interrupt source (below), and the cost model (`--cost f121` on
the `$A5` run, `fastpath` on the `$5A` run, `--cost-timed`,
`--cost-phase`) [R `tools/a2vm/README.md:433-512`].

**The write log.** `--write-log` takes at most 256 ranges
[R `tools/a2vm/README.md:442-444`], and the allowed set cannot be written
as ranges: `sector.validcount` alone is 250 two-byte slots at a stride of
16 in `LVMAP`. So the run logs every storage the machine has but the
stack page (`main:0000-00FF`, `main:0200-FFFF`, `lc`, `lc1`, `aux0-127`;
the stack is `--lowest-s-in`'s), with `--write-log-limit` 2,000,000 lines
(about 100 MB [A: 50 B a line]; a run that reaches it fails), and
`render_check.py` filters the log against `rlayout.py`'s allowed set byte
by byte, the writing PC included (zero page: the render overlays, the math
block and `FA_*` from render code, `$D8-$FF` from the interrupt stub
only; `$42-$47` never). The log is read as the run ends and deleted.

**A live interrupt source.** Without one, `--irq-bounds` checks nothing.
The driver enables the mouse card's VBL interrupt (mode bit 3
[R `tools/a2vm/README.md:244`]) with a stub handler in the card, which
acknowledges it, counts it in `$D8-$FF` and returns; `--cost-timed` makes
VBL follow the model's clock. `--irq-bounds` gets the stub's ranges (zero
page `$D8-$FF`, the stack page, the mouse card, the card), as
`tools/sound/run65.py` passes its player's. A frame with no interrupt
taken fails: the check is never vacuous. (Correction, stage A: a frame of
the walk alone lasts 0.4-16 ms of the model's time, often less than a VBL
period, so the correctness runs use a2vm's `--speed 1`, a VBL every
17,030 cycles, 2-31 interrupts a frame; the timing runs keep the model's
clock.) The report gives the stub's share of each phase (its count times
its cycles).

**Phase marks.** Phases nest: wall setup (9) runs inside the BSP walk (3)
and the seg loop (10) inside wall setup, so a driver cannot mark them
around parts. The `rprof` build marks the transitions in the code, at
upstream's places [R `r_bsp65.s:906-911`, `r_wall65.s:935-938`]: before
and after the call of `nr_storewall` (9, then back to 3) and of
`nr_segloop` (10, then back to 9), plus 2 at `nr_frame` entry and 3
before `nr_bsp`; the phase loader marks 1. a2vm's phase is the value
written divided by 2 [R `tools/a2vm/main.c:78-79`], so each mark writes
2 × n to `$0300`, as milestone 5's `MARK` does [R `src/native/replay.s:73-83`].
Upstream's own `PHASE` writes n [R `r_bsp65.s:89-92`]: only the numbers
and places are upstream's. The far windows of each phase count in it.

### 4.3 Comparisons: `tools/native/rcanon.py`

Both machines' outputs become one canonical form; the diff is exact.

- **Records.** Upstream: for each column, the records of every early flush

- **No stray writes:** the write log (4.2), filtered against `rlayout.py`'s
