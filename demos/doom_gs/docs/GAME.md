# The game logic

The tic phase: every routine of upstream's game units that a game tic
reaches, rewritten in 65C02 assembly and kept bit-exact with upstream's
65816 code (Doom8088: Apple IIgs Edition, the release this port
follows). It
covers the tic loop, the mobjs and their states, the map code, sight and
sound, the monsters' AI, the player, weapons, pickups and damage, the
world's movers and specials, and the game flow up to the screens. The
level it runs on is loaded by [`LEVELS.md`](LEVELS.md); the main loop,
the kernel and the images' loads are [`PLAY.md`](PLAY.md); the speed work
on the paging and the copies is [`SPEED.md`](SPEED.md); addresses are
[`MEMORY_MAP.md`](MEMORY_MAP.md).

Upstream file citations (`p_map65.s:326` and so on) are to
`build/upstream/src/iigs/`.

## 1. Overview

| Piece | Sources | Role |
| --- | --- | --- |
| The runtime | `gobj.s`, `gcall.s` | The object API (5), the code paging and the dispatch tables (7, 8), the memory-API transport in the card |
| The game core | `gthink.s`, `gpos.s`, `gspawn.s`, `gweap.s`, `gvalid.s`, `gspec.s` | The level setup's routines ([`LEVELS.md`](LEVELS.md) 4.3), shared by the load image and the tic image: the thinker list and pools, `P_Random`, positions and sector nodes, the spawn, the weapon's raise, `validcount`. `gspec.s` (`P_SpawnSpecials`) is linked into the load image only |
| The 29 parts | `src/native/game/<part>/*.s` | The rest of the game logic (4) |
| The tables | generated by `tools/native/glayout.py` | Every place, the placement, the dispatch tables, the link map |
| The glue | `dl_*.s`, `s2t_*.s`, `fx_chan.s` | The main loop's brain, the tic command, the hooks and the tic-side 2D and sound modules: [`PLAY.md`](PLAY.md), [`SCREENS.md`](SCREENS.md) |

Each frame the kernel loads the tic image's core into W, the brain runs
the frame's tics (`G_Ticker` each), and the frame's list hands W to the
render phases ([`PLAY.md`](PLAY.md) 2). The core holds the hot code; cold
routines live in groups that `FCALL` pages into one of two W slots or
into a frame slot in main memory (7).

The native tic was compared with upstream's on the reference machine
(`tools/ref816`) tic by tic, its whole canonical game state equal at every
tic of the three demos, a new game, the tour of E1 and generated input
streams.

## 2. Sources and build

### 2.1 The build

`src/native/play.mk` builds the tic image (`build/native/play/tic/`):

1. `glayout.py --out build/native/play/tic` writes `gen/ggame.inc`
   (every place of the tic phase, the zero page, the scratch blocks, the
   stop codes, upstream's constants `UC_*`, `UO_*` read from
   `offsets.inc` and `info.inc` through `tools/bridge/incfile.py`),
   `gen/gplace.inc` (each routine's group, the groups' slots, the frame
   slots, the `FCALL` and `ROUTINE` macros), `gen/gdisp.inc` (the five
   dispatch tables) and `game.cfg` (ld65's map: W's areas, the core,
   each group at its slot's address in a file of its own).
   `playlink.py --tic-cfg` adds the glue's groups to make `play.cfg`.
2. Every source is assembled with `-D PLAY_TIC`; the game's math is
   `math.s -D GAMEMATH` (`math-g.o`: `R_PointToAngle3`, the sines,
   `P_AproxDistance`) beside the render subset `math-r.o`.
3. ld65 links `tic.*`. An area that overflows fails the link.
4. `tools/native/playdisk.py` packs the core and every group into
   `GCODE0` and `GCODE1` (bank file `CODE.2`) and writes the group
   directory (`grp_bank`, `grp_src`, `grp_pages`, `grp_tail`) into the
   core (`tools/native/grun.py`'s `group_entry`).

The placement (which routine is in the core, which in which group and
slot) is data: `build.sh` copies `tools/native/gplace-f122.json` to
`build/native/game/shared/placement.json`, which `glayout.py` reads.
Moving a routine changes no source. `tools/native/gcallgraph.py` reads
upstream's game units with our own front end (`tools/v816/frontend.py`,
never upstream's assembler or `cal_integer.s`) into a call graph keyed
`file:label`; `glayout.py` takes the states' actions (`ACTTAB`'s order)
and the routine heads from it.

### 2.2 The parts and `integrated.txt`

Each part is a directory `src/native/game/<part>/` with its sources and
a fragment `part.mk`:

    PART := tic
    WAVE := 6
    tic_SRC := game/tic/gtick.s game/tic/ptick.s
    tic_ENTRIES := G_Ticker P_MapEnd P_Ticker P_RunThinkers P_MobjThinker

The parts were written in six waves, each wave's direct callees in
earlier waves. `src/native/game/integrated.txt` holds the last wave
merged; `play.mk` links the parts whose `WAVE` is at most that number,
and `glayout.built_set()` marks the same parts built in the tables. It is
6: every part is built. A call or dispatch entry of an unbuilt part would
assemble to the stop `GS_UNBUILT` (or `GS_UNBUILTD`) instead of the
target.

## 3. The layouts

`tools/native/llayout.py` holds the game state's layouts (shared with the
load image); `glayout.py` adds the tic phase's. No part's source names
an address: every place comes from the generated includes.

Objects are handles, not addresses: a mobj is its slot (0-2,025: the
pool's `poolsize` slots, then the zone's), a special `$0800` + its slot,
a sector a byte, a line, side, subsector, seg, node or sector node a
16-bit index; `$FFFF` is none. Fields keep upstream's widths where the
arithmetic needs them (fixed point and angles 4 B) and shrink where a
value is a handle or a byte by construction.

### 3.1 The mobj

A slot is a `RTHING` slot and three game groups at the same address
(`$0200` + 24 × slot) in three banks, plus four bytes in the planes:

| Group | Bank | Fields (bytes) |
| --- | --- | --- |
| `RTHING` | 50 `RTH` | x, y, z (4 each), angle high (2), sprite (1), frame (2, bit 15 full bright), flags (1, bit 0 `MF_SHADOW`), snext (2), angle low (2), 2 spare: the renderer's part ([`RENDER-MASKED.md`](RENDER-MASKED.md)) |
| A | 69 `MOBJA` | thinker prev (2), type (1), sprev, bnext, bprev, subsector, touching sector list, state, health, target (2 each) |
| B | 70 `MOBJB` | floorz, ceilingz, dropoffz, radius, height, flags (4 each) |
| C | 71 `MOBJC` | momx, momy, momz (4 each), move direction, threshold (1 each), pursue count, move count, reaction time, last enemy, `sightline` (2 each) |
| Planes | 74 `MOBJP` | thinker next (low and high planes), kind (the thinker function's number, bit 7 `CLEAN`), tics (a byte, `$FF` for -1) |

Upstream's kind cache (mobj byte 11) is the kind plane's `CLEAN` bit.
Every state's tics is -1 or 1-12, so the tics plane is a byte, as
upstream's walk already assumes.

### 3.2 The thinker list and the planes

The list runs from `G_THFIRST` to `G_THLAST`: a mobj's next in the
planes, its prev in group A; a special's both in its record. During the
tic phase the four walk planes (`TNL`, `TNH`, `KIND`, `TICS`, 768 bytes
each) sit in W at `$B400-$BFFF`; the kernel copies in each plane's pages
below the high-water slot `G_MOHWM` and `dl_disp.s`'s `planes_out` writes
them back. A thinker visit then needs no far access for its next, kind
and tics. A mobj slot past 767 is the stop `GS_PLANES`, below upstream's
own zone limit.

The thinker functions (`llayout.FN`): mobj, brainless mobj, the two
delayed removals, plat, door, floor, light flash, strobe, glow, scroll,
and a free zone slot. A removed special keeps its record until the walk
reaches it, with the delayed-removal function.

### 3.3 The specials

`ZONE0` (bank 75), 32-byte records, one range of slots a kind: plat,
door, floor 256 each; light flash, strobe, glow, scroll 128 each. Each
range has a free list (`G_SPFREE`, a head a kind). A record holds the
thinker links and function (bytes 0-4), the sector (5) and its kind's
fields from 6 on (`llayout.SP_KIND`). Upstream keeps no list of active
plats, so the plat's list field is always none. A full range is the stop
`GS_SPECIALS`.

### 3.4 The player and the globals

The globals block is main `$1C80-$1EF8` (after `LNMAP`, `$1B80-$1C7F`),
persistent across frames and loads. The player comes first (148 B):
upstream's `player_t` fields in upstream's order, with `mo` and
`attacker` as mobj handles, the psprites' states as state numbers and
`message` as a symbol reference (`llayout.player_layout`, from the
bridge's schema in `tools/bridge/schema.py`). Then the button list, the
pool's bitmap, the list heads, the level's globals (`gs_spawn` sets
them), the game flow's globals (`gameaction`, `gamestate`, `gametic`,
the totals, `wminfo`, the demo's pointers, the command ring `G_CMDS`),
and the tic phase's own:

| Global | Why |
| --- | --- |
| `CS_PREV1`, `CS_PREV2`, `CS_PREVR` | `P_CheckSight`'s last pair and answer (6) |
| `G_LROK`, `G_LRUSE`, `G_LRN`, `G_LRLINES` | The line record of `lineBlocks`: `P_CheckPosition` writes it, `mvNodes` reuses it (6) |
| `G_SPFREE`, `G_ZMFREE`, `G_MOHWM` | The specials' and zone mobjs' free lists; the planes' high-water |
| `G_LOADACT` | The action that started a load (9) |
| `G_SHOWMSG`, `G_MSGKEEP` | `showMessages` and `_g_message_dontfuckwithme`: `HU_Ticker` clears the message only when allowed |
| `wi` counters | `wi_stuff65.s`'s game-side state: they decide the tic of the next load |
| `G_LTABAT`, `G_FLIDXAT`, `G_FLENTAT`, `G_BLINKSAT`, `G_REJECTAT` | The map's tables in `LVG1` and `LVG2` |

After the block, `G_WSET` (the window's set, for the load's texture
reset, 9), `G_FPSSHOW` (`idrate`) and `G_ONGROUND` (`P_PlayerThink`'s
`onground`), to `$1EFB`. `P_Random`'s and `M_Random`'s indexes are main
`$03EE` and `$03EF`.

### 3.5 Sectors, lines and `LVS`

| Object | Native |
| --- | --- |
| Sector | `LVMAP` render record (16 B: heights, pics, light, `validcount`, thing list head) and `LVG1` game record (32 B: sound origin, sound target, line count, line table start, floor and ceiling data, touching thing list, special, old special, tag, sound traversed) |
| Line | `LVG0`, 32 B; `r_flags`' `ML_MAPPED` is a bit in `LNMAP` |
| A line's two sectors | `LVS` `LNSECF`, `LNSECB`: a byte each (the front twice for a one-sided line), upstream's `LNSEC` |
| Reject rows | `LVS` `RJROW`: sector × numsectors, upstream's `SS_ROW` |
| Subsector's sector | The `LVMAP` subsector record (the load's `GROUP` writes it), in place of `SS_SEC` |
| The sight hint | `MOBJP` `HINTL`, `HINTH`: a line + 1 by pool slot (6) |

Upstream's other bank-`$21` tables are not needed: `SIGHTLOG` and
`LINELOG` are a log fast path of the side test that decides only when
the exact product does too, so the native computes the exact signed
product; `SEC58`, `LN36`, `BMROW` are address tables.

### 3.6 The intercepts and the trace

An intercept is 6 B (frac 4, then a line number or `$8000` + a mobj
handle); the list holds 64 (`MAXINTERCEPTS`) with a by-frac chain of a
byte a link, in GW. The trace (`_g_trace`), the walk's state and
`P_PathTraverse`'s flags live in GW and the parts' scratch: nothing of a
traversal lives from one tic to the next.

### 3.7 Banks

The tic phase's banks besides the level's ([`LEVELS.md`](LEVELS.md) 3.3):

| Bank | Name | Content |
| ---: | --- | --- |
| 72, 73 | `GCODE0`, `GCODE1` | The tic image: the core at its W addresses, then every group |
| 74 | `MOBJP` | The walk's planes and the sight hint planes |
| 91 | `DEMOB` | The demo lump the title loop plays (DOOM1.WAD's DEMO3), with a small directory (`glayout.DEMOB_LAYOUT`) |
| 111 | `LVS` | `LNSECF`, `LNSECB`, `RJROW` |

`llayout.bank_map()` still reserves bank 92 (`GTEST`) and banks 123-124
(`LOGTAB`); the play build uses neither.

## 5. The object API

The parts and the game core read and write game objects only through
`gobj.s`; no part calls `far_get` or `far_put` on a game record.

| Call | Does | Cache |
| --- | --- | --- |
| `mo_get` (slot in A:X) | The mobj's `RTHING` and groups A, B, C into a line; `GC_MP` its pointer | main `$0C00-$0EFF`, 8 lines of 96 B, write-back by group |
| `mo_dirty` (group mask) | Marks groups to write back | |
| `mo_store` | A new mobj into its slot's line, every group dirty, the old record not read (a spawn) | |
| `sec_get` (sector) | The `LVMAP` render record and the `LVG1` game record; `GC_SP` | main `$1680-$17FF`, 8 lines of 48 B |
| `ln_get` (line) | The `LVG0` record and its two sectors from `LVS`; `GC_LP` | W `$AE00`, 8 lines of 34 B |
| `sp_get`, `sp_store` (special) | The record; `GC_XP` | W, 5 lines of 32 B |
| `nd_get`, `sg_get`, `ss_get` | A node, a seg, a subsector into a fixed buffer | none |
| `bl_get` | 256 B of the blockmap into main `$0200-$02FF` | none |
| `sd_get`/`sd_put`, `lt_get`, `bk_get`/`bk_put`, `sn_get`/`sn_put`, `mi_get`, `hn_get`/`hn_put`, `rj_row`, `rj_byte` | A side, a line-table or flood entry, a blocklink, a sector node, a `mobjinfo` word, a sight hint, a reject row or byte: the tic image's uncached records | none |
| `pl_get`, `pl_put`, `pl_setn` | A slot's next, kind and tics in the W planes | |
| `go_flush` | Every dirty line back, then every line empty | |
| `go_reset` | Every line empty, nothing written; the page-1 window code copied in | |

A get searches the recency order from its front and moves the line
there; the victim is the least recently got line, so the four most
recently got lines of a kind are never evicted (hence 5 special lines).
A pointer stays valid until the next get of its kind that misses;
routines keep handles across calls and get again, where upstream keeps
`[dp],y` pointers. One copy of each object exists in fast memory, so a
callee holding the same mobj sees its caller's changes.

A miss copies all of a record's parts in one `RAMRD` window and the
victim's dirty parts in one `RAMWRT` window, through a small routine in
page 1 (`$0100-$014F`) that `go_reset` copies there. The tic phase ends
with `go_flush` (the render phases overwrite the caches' main memory);
every entry of a tic phase begins with `go_reset`. The load image links
the same file with `-D LOADIMG`.

## 6. Native choices

**`validcount` is one count.** Upstream's game walks and
`R_RenderPlayerView`'s setup raise the same `validcount`, and the sound
flood reads the renderer's sector stamps. Natively the game's `G_VALID`
is the frame block's `VALIDCOUNT`, raised by `gvalid.s`'s `gv_inc` from
both the game and the renderer's `nr_setup`. Every increment clears
every stamp when the count wraps, the game's through the object API's
`go_stamps0`, the renderer's with its own clear (`-D GV_RENDER`), and
the count becomes 1. [`LEVELS.md`](LEVELS.md) 6 has the details.

**`P_CheckSight`'s last pair is state.** A call with the same `t1, t2`
as the last returns the last answer without the walk and without
`validcount++` (`p_sight65.s:138-147`), so `CS_PREV1`, `CS_PREV2` and
`CS_PREVR` are kept as handles. When a zone mobj that one of them names
is freed, `gt_zfree` sets it to `$FFFE` ("stale": matches no slot).

**The sight hint is by pool slot.** Upstream's `SIGHTHINT` is a 32 KB
table indexed by `t1`'s address, never cleared; its line is tested
first, through the code that stamps lines. The answer does not depend on
the hint, but the line stamps and `mobj.sightline` do. Natively the hint
is the planes `HINTL`, `HINTH` by pool slot, never cleared but at boot.
This equals upstream's within a map and across loads whose pool base
stays; after a load that moves upstream's pool base, or for zone mobjs
(whose addresses are `Z_Malloc`'s), the stamps it leaves can differ
from upstream's.

**The line record.** `lineBlocks`' record of the last position check
(`LR_OK`, `LR_USE`, `LR_N`, `LR_LINES`: 24 lines, `$FF` for too many) is
kept: `checkpos` writes it, `trymove`'s `mvNodes` sets `LR_USE`, and
`gp_secnodes` then adds the recorded lines' sectors with no block walk
and no stamps, as upstream does (`p_map65.s:893-895`, `:1700-1726`). The
setup clears `LR_OK`.

**Upstream's shortcuts are reproduced**, since they change stamps:
`mvNodes`' `validcount++` without a walk, the early traversal of
`P_PathTraverse` and its limit, `ptStuck`'s copies, the sight test's
16-bit wrap, `P_UpdateAnimatedFlat`'s unsigned shift.

**Divides.** The divides are `math.s`'s own, with a defined result for a
division by zero. `P_InterceptVector3` uses upstream's own long division
(`p_trace65.s:405-541`), mirrored step by step; for the one input
upstream never returns from (it loops forever, `:430-438`) the native
returns `$7FFFFFFF` and counts it in `GT_DIV0`.

**Not ported:** upstream's path guard (`guardL` and its helpers, 1,284 B:
`early` branches over its only call, `p_path65.s:612-614`);
`P_SetSeclist` (no unit calls it); `R_GetTexture`'s textures made in play
(every texture is resident). After a load `g_resume` resets
`texturetranslation[n] = n` for the textures upstream's load would make,
which only `P_UpdateSpecials` changes (`glayout.txr_compute` gives the
masks by map; `G_WSET` tells whether `W_LevelDone` ran).

## 7. Calls and code paging

### 7.1 `FCALL`

A part calls another routine with the `FCALL` macro (`gplace.inc`).
When the target is in the caller's group or the core, it is `jsr`. Else
it is `jsr fc_call` followed by three bytes (the target's group and
address). `fc_call` (`gcall.s`):

1. saves the target slot's need (`SLOT_NEED`: the group the slot's
   innermost active `FCALL` frame needs, `$FF` none) on the stack, one
   byte;
2. makes the target's group the slot's need and loads it with `gr_load`
   only when the slot holds another group;
3. calls the target (A, X, Y passed both ways, P returned);
4. on return restores the saved need and reloads that group only when
   the slot now holds another, whoever the caller is.

A frame that returns into a slot always finds its group there; a group
no active frame needs is not reloaded. A cross-group call costs 5 bytes
of stack. The kernel resets `SLOT_GRP` and `SLOT_NEED` at each tic phase
(`K_TIC`), so a slot's bytes after a load or a frame are never taken for
a group.

`gr_load` copies a group by one memory-API PRIVATE request (`am_one`),
its length from the group directory. The transport (`am_begin`,
`am_push`, `am_fin`, the request template `am_req`) is `gcall.s`'s
segment `AMEMLC` in the main card's bank 1 at `$DB5C-$DBFF`; without the
memory API, `DOOM.SYSTEM` patches it with a CPU copy
(`tools/native/amcpu.py`).

### 7.2 The slots

| Slot | Where | Holds |
| --- | --- | --- |
| core | W `$6600-$99FF` (13,312 B) | The runtime, the game core, the game's math, the hooks' entries, the dispatch tables, and the routines the placement puts there |
| 1 | W `$9E00-$A5FF` (2,048 B) | One group at a time |
| 2 | W `$A600-$ADFF` (2,048 B) | One group at a time |
| 3-17 | main `$2000-$5FFF` | Frame slots: one pinned group each, at a place of its own |

Main `$2000-$5FFF` holds the replay's colormaps A and B, which only the
replay reads. During the tic phase a pinned group runs there: `gr_load`
copies it in by a PRIVATE request at its first call in a frame (a CPU
store there would be a video write), and it stays until `K_TIC`. At the
tic phase's end the brain calls `fs_restore`, which copies back every
loaded slot's colormap bytes from the level's copy in `LVC` in one
request, a descriptor a slot (so at most 15 frame slots). A frame slot is
its group's bytes plus 96, in pages, none across `$4000`. No routine
that stores into its own group's bytes (the flood's work stack) is
pinned.

### 7.3 The placement

`tools/native/gplace-f122.json` places the 29 parts and the game core:
42 groups (20 in slot 1, 11 in slot 2, 11 in frame slots 3-13 using all
64 pages), and the core's table routines (`P_CheckSight`, `sightSlope`,
`P_TryMove`, `P_Ticker`, `P_MapEnd`, `P_MovePsprites`, `A_WeaponReady`
and the other psprite routines, `wInfo`). It was searched (repair,
sweeps and annealing) on recorded call traffic, pricing each load as
a2vm's model of the memory API on the card runs it; [`SPEED.md`](SPEED.md)
has the cost model. Its rules:

- `A_Chase` and its callees (`P_NewChaseDir`, `P_Move`, `P_TryWalk`) are
  never in one slot: `A_Chase` runs about six times a tic and calls them
  on most calls;
- `APART` pairs: `traverseTo` and each `TRVTAB` traverser; `T_VerticalDoor`
  and `T_MovePlaneCeiling`;
- affinity units stay together (the walk with `P_MobjThinker` and the
  light thinkers; `P_XYMovement` with `P_TryMove` and `slideMove`; each
  part's own units);
- each group within its slot less a margin (96 B), the core within its
  room less 16 B;
- no frame slot for a routine the tic code stores into.

The search that produced the file is not in this tree; the file is the
result. `playdisk.py` checks it against the play link: no absolute store
of the tic image's code into `$2000-$5FFF`, each pinned group inside its
frame slot.

## 8. The dispatch tables

Upstream calls five families of routines through pointers. Each is a
table in `gdisp.inc`, three bytes an entry (the target's group and
address), called with `DCALL table, number` (`dc_call`, through
`fc_call`'s path); 0 is none.

| Table | Dispatcher | Entries | Upstream |
| --- | --- | --- | --- |
| `ACTTAB` (30) | `P_SetMobjState` (`mobjstate`), `setPsprite` (`gweap.s`) | Every action the states name, in `info65.s`'s order, and `A_CyberAttack` (the rocket cheat): `look`, `chase`, `pspr`, `wfire`, the game core's `A_Raise` | `JML [FN_P]`, `JML [ACT_JMP]` (`p_tick65.s:533`, `p_pspr65.s:118`) |
| `THTAB` (11) | `P_RunThinkers` (`tic`) | `P_MobjThinker` (`tic`); the brainless thinker and the two delayed removals (`mobjstate`); the lights and `T_Scroll` (`secfind`); `T_MoveFloor` (`planes`); `T_PlatRaise`, `T_VerticalDoor` (`movers`) | the walk's `call` (`p_tick65.s:303-317`) |
| `ITTAB` (4) | `P_BlockLinesIterator`, `P_BlockThingsIterator` (`geom`) | `PIT_AddLineIntercepts` (`tracel`), `PIT_AvoidDropoff` (`chasemove`), `PIT_RadiusAttack` (`look`), `stompThing` (`teleport`) | `callLN`, `callLN2` |
| `TRVTAB` (5) | `P_PathTraverse` (`path`) | `PTR_AimTraverse`, `PTR_ShootTraverse` (`attack`), `PTR_SlideTraverse` (`xymove`), `PTR_UseTraverse`, `PTR_NoWayTraverse` (`player`) | `callTrav` |

`act_num` turns a state's action (upstream's address in the `states`

## 9. The tic phase

### 9.1 Memory

W:

| Range | Content |
| --- | --- |
| `$6000-$65FF` | `MATHW`, `AUXW`: the render images' bytes |
| `$6600-$99FF` | The core |
| `$9A00-$9DFF` | The parts' scratch blocks |
| `$9E00-$A5FF`, `$A600-$ADFF` | Slots 1 and 2 |
| `$AE00-$B3FF` | GW: the line and special caches, the intercepts and their chain, the record buffers (`LW_MOB`, `LW_STATE`, `LW_NODEB`, the seg, subsector, map thing, special, sector node and line buffers), then the tic phase's shared near fields (`GM_*`: the line opening, `tmfloorz`/`tmceilingz`/`tmdropoffz`, `tmthing`, `tmx`, `tmy`, `tmbbox`, `spechit`, the trace, `linetarget`) |
| `$B400-$BFFF` | The walk's planes, 768 slots |

Main ranges the tic phase overlays, each dead between the replay's end
and the next frame's front end (`glayout.check()`, run whenever it
writes `ggame.inc`, asserts it against `rlayout.py`'s region list): `$0200-$02FF` (`bl_get`'s buffer), `$0C00-$0EFF`
(the mobj cache), `$1680-$17FF` (the sector cache), `$1980-$1A7F` (the
runtime's state: the caches' tags and recency orders, `SLOT_GRP`,
`SLOT_NEED`, `FS_DIRTY`, the walk's thinker and next, `MP_MODE`), and
the frame slots in `$2000-$5FFF`. The language cards are unchanged but
for `AMEMLC`; the aux card's tables serve `R_PointToAngle3` in short
`ALTZP` windows.

Main zero page in the tic phase:

| Range | Owner |
| --- | --- |
| `$00-$17` | Platform, far layer |
| `$18-$37` | The game core (`GC_*`) |
| `$38-$3F` | The object API's pointers (`GC_MP`, `GC_SP`, `GC_LP`, `GC_XP`) |
| `$40-$41` | `gcall.s` |
| `$48-$5B` | `GA_*`: a call's arguments, written by the caller, read by the callee at its start (upstream's `_Dp[0-15]` and stack arguments) |
| `$5C-$74` | `GT_*`: temporaries any call may change |
| `$75-$AF` | The spawn's (`GS_*`): temporaries of every caller of `P_SpawnMobj` |
| `$B0-$D7` | The math |
| `$D8-$FF` | The IRQ |

A part has no zero page of its own. What it keeps across a call goes in
its scratch block in W `$9A00-$9DFF`: 32 B by default, more on request
(`sight` 106, `path` 44). Two blocks share bytes only if no routine of
one can be active while one of the other is.

The stack budget is 160 B plus 24 B for the IRQ. Natively returns are 2
bytes and arguments are in `GA_*`; each cross-group call adds 5 B. The
IRQ handler touches only zero page `$D8-$FF`, the stack, the card's
`$E000-$FFFF` and I/O, so the object API's windows and the group copies
run with interrupts on.

### 9.3 The load protocol

Upstream's `G_Ticker` loads a level inside an action (`loadLevel`,
`doNewGame`, `doPlayDemo`, `doWorldDone`, each ending in `doLoadLevel` →
`bmLoad` → `P_SetupLevel`) and then goes on in the same tic: code runs
after the load inside the action, then the action loop tests
`gameaction` again, copies the command and runs `P_Ticker`
(`g_game65.s:563-669`, `:877-884`, `:1100-1142`, `:1205-1311`).

Natively `flow`'s action runs up to the load (`doLoadLevel`'s part
before `bmLoad`), stores the action in `G_LOADACT` and `G_Ticker` returns
`GT_LOAD`. The brain hands the kernel the load list (`dl_disp.s`
`c_loadlist`: the busy sign, `LCODE`'s `nl_setup(G_GAMEMAP)`, the sign
off), and the next tic phase enters at `E_RESUME`: `g_resume` runs the
continuation of `G_LOADACT`'s action (`doLoadLevel`'s tail, then the
action's own: for a new game `gameaction` 0 and `ST_Start`; for a demo
`player.cheats` 0, `usergame` 0, `demoplayback` 1, `starttime` from
`I_GetTime`; after the intermission `gameaction` 0) and the texture
reset of 6; the keys go up, `S_Start` runs; then `G_Ticker` re-enters
its action loop at the test of `gameaction` and the frame's other tics
follow. Nothing but persistent memory lives across the load: the core's
own variables return to their image values when the core is reloaded.

### 9.4 Hooks

The tic image calls the screens and sound through hooks (`dl_hook.s`,
[`PLAY.md`](PLAY.md)): `S_StartSound`, `S_StartSound2`, `S_StopSound`
(the effects' channels), `I_GetTime` (the platform clock), `AM_Stop`,
`ST_Start`, `HU_Start`, `F_LoadScreen`, `D_PageTicker`, `D_AdvanceDemo`,
`W_StartInter`, `W_StartFinale`, `F_Ticker`, the status bar's and HUD's
tickers, `G_TimeDemoEnd`; `AM_Ticker` and `Z_CheckHeap` do nothing.
`I_Error` and the zone's allocators are stops (`GS_ERROR`, `GS_ZONE`).

### 9.5 Stops

A stop stores its code in `GS_STATUS` (main `$03B0`) and its argument
in `GS_ARG` (`$03B1`), then executes `BRK` (`glayout.GS` names the
codes: `GS_PLANES`, `GS_SPECIALS`, `GS_FLOOD`, `GS_ACTION`, `GS_ZONE`,
`GS_ERROR` and the rest).
