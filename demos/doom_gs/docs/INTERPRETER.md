# The 65816 interpreter: cost and first contact

This file is generated by `python3 tools/a2vm/interpreter_report.py` from
the measurement files in `build/a2vm/interp/` (`--run` makes them again;
every machine involved is deterministic, so a new run gives the same
files and the same text). Do not edit it by hand. It answers items 2 and
3 of [`MILESTONES.md`](MILESTONES.md) 3.2 for the interpreter of
[`src/vm`](../src/vm/README.md): what one interpreted 65816 instruction
costs on the Appletini, against assumption P5 of
[`ARCHITECTURE.md`](ARCHITECTURE.md) section 6, and how far the
interpreter runs upstream's release in lockstep with `ref816`.

**All times are those of a2vm's cost model, not of the card.** Its
parameters are derived from the firmware's RTL (appletini-one F1.2.1)
and from the documents in [`firmware/`](firmware/), as
`tools/a2vm/costs/appletini.json` cites for each one; none has been
measured on the card, which milestone 0 will do. Profile **f121** is the
firmware as it is; **fastpath** is F1.2.1 with the seven changes of the
firmware design (quiet switches, TURBO caches that survive a mapping
change, a 16-line RamWorks cache, relaxed PSRAM admission, the lazy SHR
mirror, the `$C069` read bank). 65C02 cycles are exact: one a bus cycle
of the W65C02S, as a2vm's core makes them. The fabric runs at
133.333 MHz.

## 1. The answer

An interpreted instruction of the game, with the code page cache, costs:

| Scene | Instructions | 65C02 cycles | µs, f121 | f121 / P5 | µs, fastpath | fastpath / P5 |
|---|---|---:|---:|---:|---:|---:|
| still | all instructions | 299 | 5.33 | 1.66 | 4.43 | 1.39 |
| still | without the record replay | 297 | 5.25 | 1.64 | 4.40 | 1.38 |
| demo | all instructions | 319 | 5.74 | 1.79 | 4.60 | 1.44 |
| demo | without the record replay | 313 | 5.60 | 1.75 | 4.47 | 1.40 |

That is 1.7 to 1.8 times P5 (3.2 µs, range 3.0 to 3.9) under
f121, and 1.4 times under fastpath. "Without the record
replay" leaves out the phase the port writes by hand (`R_DrawLists`).

- **Most of the time is the interpreter's own work.** It makes 299 to 319 65C02
  cycles a 65816 instruction; P5's 3.2 µs at P1's 45 M cycles a second
  allows 144. Under fastpath, 90% of the
  time is plain accesses to fast memory (the interpreter's own code, its
  zero page and the game's direct page and stack); under f121
  73%, and the soft switches around each access to
  extended memory another 24% (0.80 bus cycles an
  instruction, 0.21 with fastpath's quiet switches).
- **The far layer is the largest part.** 54% of the 65C02 cycles are in
  `far.s`: every operand byte, even one of the direct page in main RAM,
  goes through `far_rd` or `far_wr` and its translation check (section 6).
- **P5 does not hold for this interpreter.** The frame it implies for a
  game run all interpreted, "about 1.9 s" in ARCHITECTURE.md
  section 6, becomes the one of section 8 below.

## 2. First contact with the game

The interpreter ran upstream's release image (the memory image of
`tools/ref816/make_image.py`) on a2vm, through the far layer and the
game's map of ARCHITECTURE.md 3.3 (104 RamWorks banks: the
map is described in `tools/a2vm/game816.c` and `src/vm/README.md`), from
the entry point with the registers `ref816` starts with, in lockstep with
`ref816`'s IIgs: after every instruction the harness compared the
registers A, X, Y, S, D, DBR, PBR, PC, P, E and the run state, and every
write of the instruction (address and value); at the end, all of the
mapped virtual memory.

| | |
|---|---|
| Instructions run identically | 322,215 |
| How it ended | at the first access to the IIgs I/O space |
| Difference | none |
| Next instruction of the reference | $AF `LDA long` at $04:6002 |
| Its first access to I/O | read of $E0:C036 (the IIgs I/O space) |
| Where the interpreter trapped | $E0:C036, status 1 (1 read, 2 write) |
| Virtual memory unlike the reference's, at the start and at the stop | 30,970 and 30,970 bytes, in bank $01 |

It stopped where it should: the reference's next instruction accesses the IIgs I/O space, and the interpreter trapped on that same access. These instructions are upstream's `crt0` (it clears the
BSS sections of `data_init_table` a byte at a time) and the start of
`main`, which begins by setting the IIgs's speed register `$C036`
([`research/iigs-platform.md`](research/iigs-platform.md) 1.5).

The only memory the two machines disagree on is bank `$01`: the game's
map gives banks `$01` and `$E1` the same memory (base aux, identity,
ARCHITECTURE.md 3.3), so the interpreter sees the title picture the
loader left in `$E1` at `$01:2000-$9FFF` too, where the IIgs has zeros
(30,970 bytes). They differ the same way at the stop: no instruction of the run wrote them, and one that read them would have shown in its registers. The image bytes the map
leaves out: 1,769,321 bytes of the level store in banks $40-$5B; the two bytes of the loader's memory probe in each of 47 banks the map leaves out; 6,553 bytes of bank $E0 (the copies the shadow register made of the text and hi-res pages of bank $00).

## 3. How the cost is measured

The cost of an instruction is the 65C02's work from the moment the
dispatch loop fetches its opcode (`fetch` in `src/vm/core.s`) to the
moment it is ready to fetch the next one: the dispatch, the handler, its
addressing mode, its operations and far accesses, and the loop's test of
`vm_event`. The service of an event is left out: the one event of
ordinary code is a change of code page, which section 5 measures apart.
Three measurements use that definition:

1. **The game's own instructions.** `ref816` runs the two scenes of
   [`PROFILE.md`](PROFILE.md) (standing still in E1M1, the title demo)
   and writes one instruction in 499 of the recorded frames
   whole: its registers, every byte it read and wrote, the registers
   after it (`tools/ref816/trace.h`, "Samples"). `game816 samples` runs
   each on the interpreter with the game's map and every bank below `$40`
   mapped, with the bytes it read at their places, after setting the far
   layer's bank as the last extended-memory access before it left it;
   then it compares the registers and the writes with the reference's.
   Being every 499th instruction, their mean is the cost
   weighted by the game's mix, with the addresses the game really uses.
   An instruction whose bytes lie in two code pages, or that starts a
   page, is run twice and measured the second time, so that the copy of
   a cold page is not in its cost, and the lookup of the page its fetch
   enters is set apart: the code cache's share (section 5) counts it. 56,167 instructions were measured (the two
   profiles run the same ones), with 0 differences.
2. **The vectors.** `vm816 --cost` runs every SingleStepTests 65816 case
   through `vm_run` and measures it the same way (section 9), with
   0 differences in the checks of registers and memory
   (the 44 known issues of the set aside, as in milestone 2).
3. **The code page cache.** `game816 pages` measures what a change of
   code page adds, when the page is in the cache and when it is not; the
   trace counts the changes and the misses of a model of the cache in
   the game's own order of execution (section 5).

The cost model runs beside the machine. It carries its caches from one
instruction to the next; the TURBO caches hardly matter here: the simple
instructions of the first contact, which ran in a loop, cost the same as
the same instructions in the samples, which ran one by one.

## 5. The code page cache

The interpreter copies each page of code it runs into one of
16 slots of main RAM (`src/vm/README.md`, "The code cache"). A jump,
a branch, a return or a fall-through to another page costs the service of
`EV_PAGE` and a lookup of the slots; a miss also copies 256 bytes out of
extended memory. `game816 pages` measures it with loops of `JMP abs`
through 1, 16 and 20 pages of bank `$03`:

| Profile | JMP in its page: cycles | µs | A change of page, cached: more cycles | µs | A change of page, not cached: more cycles | µs |
|---|---:|---:|---:|---:|---:|---:|
| f121 | 111 | 1.80 | 318 | 4.86 | 4,761 | 73.03 |
| fastpath | 111 | 1.80 | 318 | 4.86 | 4,761 | 70.54 |

The trace models the cache (TRACE_CODE_SLOTS pages, filled in turn, as
`src/vm` does) in the game's own order of execution and counts the
changes of page and the misses; the product is the cache's share of an
instruction, which section 1 adds to the samples:

| Scene | Instructions | Changes of page an instruction | Missed | Misses an instruction | µs an instruction, f121 | µs, fastpath |
|---|---|---:|---:|---:|---:|---:|
| still | all instructions | 0.050 | 8.8% | 0.0044 | 0.54 | 0.53 |
| still | without the record replay | 0.049 | 13.1% | 0.0065 | 0.68 | 0.66 |
| demo | all instructions | 0.039 | 10.2% | 0.0039 | 0.46 | 0.45 |
| demo | without the record replay | 0.049 | 12.1% | 0.0059 | 0.64 | 0.63 |

The far layer's work is the same for every operand byte: translate the
address (`resolve`: compare the bank and page with the last translation,
walk the map or the page table otherwise), then either read main RAM
directly or switch `RAMRD` or `RAMWRT` (and `$C073` when the bank
changes) around one access to extended memory, and check the write watch
of the code cache after a write. An 8-bit `LDA [dp],y` makes four such
calls. Section 1's figures follow from this design more than from the
memory system: with fastpath's quiet switches, 90%
of the time is still the 65C02 running from fast memory.

The vector medians overstate the game's cost: a vector case puts the
direct page, the stack and the data at random addresses, which the
harness maps into extended memory, mostly in another bank than the
code, so that most operand bytes cost a switch of `RAMRD` or `RAMWRT`
and often of `$C073`. The game keeps its direct page and stack in main
RAM (`$00:0900` and `$00:3000`), and its data mostly in bank `$02`. The
vector minimums, where the operands happen to cost least, understate it.
The game's own instructions are the figure to use; the table shows why
the per-opcode medians of section 9 are not.

## 8. Against assumption P5

page cache. In 65C02 cycles, at P1's 45 M cycles a second:

|---|---:|---:|---:|---:|
| still | 299 | 144 | 2.1 | 6.65 |
| demo | 319 | 144 | 2.2 | 7.08 |

And the frame of a game run all interpreted ("Tier 0" of ARCHITECTURE.md
section 6, "about 1.9 s"), with PROFILE.md's instructions a
frame and the costs of section 1 (the interpreter's time only: no I/O,
no platform layer, the replay interpreted too):

| Scene | Profile | Instructions a frame (median, PROFILE.md) | Frame, all interpreted | Frames a second |
|---|---|---:|---:|---:|
| still | f121 | 331,325 | 1.76 s | 0.57 |

| demo | f121 | 461,187 | 2.65 s | 0.38 |
| demo | fastpath | 461,187 | 2.12 s | 0.47 |

What it changes: the interpreter is tier 0, for cold code; the
architecture puts 97 percent of the instructions in translated code
(P4). At the measured cost the 3 percent it leaves to the interpreter
take 1.4 to 1.8 times the 43 ms that section 6 of
ARCHITECTURE.md gives them. The first places to look are the far layer's path for the direct
page and the stack (in main RAM, yet translated byte by byte), and the
lookup of the code cache on a change of page.
