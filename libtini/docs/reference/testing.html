Checks and status

How to run the checks, what each kind of evidence can and cannot show, and what still needs a board.

Three kinds of evidence

KindRunsShows
HostPython tests of the tools, and the C game logic and input code compiled with GCCFormats, compilers, game rules, determinism
EmulatorThe linked 65C02 programs on py65 with independent memory and device models, and on the repository's native Appletini machine at the vtw33 and turbo-f122 modelsThat the actual compiled code produces the right bytes, register writes and results, and model timing
BoardThe disks on an Appletini //eReal timing, output, sound and input; nothing else establishes these

The models do not include the Appletini capture stream, HDMI presentation, bus contention or physical interrupt latency. turbo-f122 uses historical F1.2.2 costs, not complete F1.3.2 timing.

Run every check

python -m pip install py65==1.2.0
python tools/check.py --cc65-home D:/Repos/cc65 --cc C:/msys64/ucrt64/bin/gcc.exe [--rom-boot] [--only NAME,NAME]

The runner builds both variants and runs each check in order, stopping at the first failure. Logs go to build/checks/NAME.log and results to build/checks/validation.json. --only reruns named checks and keeps the other recorded results. --rom-boot adds real ProDOS boots, which need the separately installed ROMs under build-inputs/native-roms/. The Python that runs it must have py65 1.2.0, and GCC's folder must be usable for the native machine.

Status

The selected board baseline is existing Appletini firmware F1.3.2, commit 73de6fe03c31ad6f8ebfce3328704761fcd8c5a2. It differs from the earlier F1.3.1 baseline in speech clocking, ONE//e video timing and USB input; the slot-7 ROM, the AMEM service and RamWorks are unchanged. The full set of checks, ROM boots included, passed for the build of 2026-10-22.

Board observations so far are by eye, not recorded tests. On 2026-10-21 the owner played STARFALL in standalone ONE//e mode with a physical Apple joystick: before the joystick reader waited for running paddle timers, the pause panel's readout jumped back while the stick moved right or down; with the wait, the jumps were gone. Which paddle path ran, its interrupt retry and the calibration thresholds were not measured. On 2026-10-22 the owner played the build with the faster text and publication and saw no visible difference in play between TURBO, 33 MHz and 26 MHz. Effect volumes were set by listening on the board. On F1.3.1 in standalone ONE//e mode the SSI-263 had no clock and speech timed out, as examples/speech_check showed; the owner reports that F1.3.2 fixes this.

Board checks still to run

On the installed F1.3.2 baseline, without rebuilding or flashing firmware, at 33 MHz and in TURBO:

  • Boot the disks with RamWorks enabled and selectors 1-2 (diagnostic) or 1-3 (starter, STARFALL) free. Confirm the diagnostic's full SHR screen and five PASS results, and a normal return to the ProDOS launcher.
  • Put known files on /RAM before launch and check their data after exit.
  • Measure the longest interrupt-masked burst, memory-operation latency and the cost of full and dirty screen publication. No bandwidth, frame deadline or clock accuracy is established on a board yet.
  • Calibrate the VIA clock source, compare simulation, music and speech rates across both speeds, listen to pronunciation and ducking, and confirm AY pitch and envelopes.
  • Play STARFALL and the starter with a keyboard and joystick: held keys, rest calibration, all four directions, the pause readout, game over, retry and a clean exit.
  • Save and load files while SHR is shown, including an ordinary disk error.
  • Compare the CPU-only build with the AMEM build, with the service available and unavailable before submission; video stays on CPU writes throughout.
  • Check missing speech hardware, smaller-memory failure messages and visible publication gaps.
Check scripts are in tests/; the runner is tools/check.py.
