libtini

Builds and game manifests

tools/build.py builds the library, the SDK programs and every game it finds, checks each linked layout and packages ProDOS disks. A game describes itself in a game.json manifest, so adding one needs no change to the build script.

Command line

python tools/build.py [--cc65-home DIR] [--game NAME] [--no-disk] [--private] [--build-dir DIR]
                      [--test-target] [--prodos-image FILE]
OptionEffect
--cc65-home DIRThe installed cc65 2.19 SDK. Defaults to CC65_HOME, then to the SDK of the cc65 on PATH.
--game NAMEBuild the library, the diagnostic, this game and any program its disk lists. Without it every manifest is built.
--no-diskLink programs and the library only; no ProDOS input is needed.
--privateCompile with TI_PRIVATE_TRANSPORT=1 and link the optional AMEM transport. Games whose manifest sets "private": false are left out.
--build-dir DIROutput folder inside the project, build by default. Use build/private for the AMEM variant.
--test-targetAlso link the 65C02 test programs that the checks run.
--prodos-image FILEUse another installed copy of ProDOS 8 2.4.3; it must match the pinned SHA-256.

What a build does

  1. Reads and checks every examples/*/game.json and games/*/game.json before building anything.
  2. Runs the selected games' generate steps, then compiles the audio demo's score and phrases.
  3. Compiles every src/*.c except the diagnostic and assembles every src/target/*.s except the startup, and archives them as libtini.lib.
  4. Links the diagnostic, the audio demo, each game and the test programs, each with the startup object, its own objects, libtini.lib and cc65's none.lib.
  5. Checks each linked layout: the SYS starts at $2000, zero page stays in $80-$9F, NEARBSS stays in the near arena, low segments stay in the readable low range, and nothing else leaves the application region.
  6. Writes the ProDOS disks, layout.json, memory.json and manifest.json, and prints one memory line per game.

The compiler commands are:

cc65 -t none --cpu 65c02 --standard c99 -O [cflags] -I SDK/include -I include -I src -I BUILD -I GAME -D TI_PRIVATE_TRANSPORT=0|1
ca65 --cpu 65c02 -t none -I SDK/asminc -I src/target
ld65 -C CONFIG -o NAME.system -m NAME.map -Ln NAME.lbl --dbgfile NAME.dbg startup.o OBJECTS libtini.lib SDK/lib/none.lib

Builds are deterministic: identical sources, flags, installed SDK and ProDOS input give identical bytes. Object timestamps are fixed, ca65's informational timestamp is normalized, and no build makes a network request. build/manifest.json records the hash of every input, tool, SDK header and output.

The game manifest

{
  "name": "starfall",
  "title": "STARFALL",
  "sources": ["main.c", "game.c"],
  "config": "examples/starfall/starfall.cfg",
  "private": false,
  "cflags": ["--static-locals"],
  "generate": [
    {
      "command": ["{root}/tools/speech.py", "{game}/speech.json", "--output", "{build}/starfall_speech.h",
                  "--symbol", "sf_speech", "--no-numbers"],
      "inputs": ["{root}/tools/speech.py", "speech.json"],
      "outputs": ["{build}/starfall_speech.h"]
    }
  ],
  "disk": {"volume": "STARFALL", "system": "STARFALL.SYSTEM", "blocks": 1600}
}
KeyMeaning
nameRequired. 1-15 characters: a lower-case letter, then lower-case letters, digits or _. Outputs are build/NAME.system, .po, .map, .lbl and .dbg. It must not repeat another game's or an SDK program's name.
titleShown in the build summary; defaults to the name.
sourcesRequired. C files relative to the manifest; the first defines main.
assemblyca65 files relative to the manifest.
configLinker layout relative to the libtini folder; cfg/libtini.cfg by default.
cflagsExtra cc65 options, such as --static-locals for foreground-only code.
privatefalse leaves the game out of --private builds; true by default.
generateCommands run before compiling, in order; see below.
diskA bootable ProDOS disk: volume (default the name in capitals), system (default NAME.SYSTEM), blocks (default 1600, an 800 KiB disk) and files.

Unknown keys are an error, as are missing sources or a missing layout file.

Generate steps

Each step is {"command": [...], "inputs": [...], "outputs": [...]}. A command whose first element ends in .py runs with the build's own Python. {root}, {game} and {build} expand to the libtini folder, the manifest's folder and the build folder. Other relative paths in inputs, outputs and disk files are relative to the manifest. Inputs are hashed into build/manifest.json, a folder counting every file under it; outputs are recorded as build outputs. The build folder and the game's folder are on the include path, so a generated header is included by its bare name.

Extra disk files

Each entry of disk.files has a name and at most one source. path copies a file; program adds another linked program, such as "libtini", the diagnostic; neither makes an empty file. Files default to ProDOS type $06 and programs to $FF with auxiliary type $2000; type and aux override them. The disk packager writes seedling and sapling files, up to 131,072 bytes each, and puts the game's SYS first so ProDOS boots it.

"disk": {"volume": "MYGAME", "system": "MYGAME.SYSTEM", "blocks": 280,
         "files": [{"name": "RESOURCES.TPK", "path": "{build}/RESOURCES.TPK"},
                   {"name": "DIAG.SYSTEM", "program": "libtini"},
                   {"name": "SAVE.A"}]}

Outputs

FileContents
build/libtini.libThe library archive
build/NAME.systemEach program as a raw ProDOS SYS file loaded at $2000
build/NAME.poEach bootable disk: the ProDOS boot blocks and kernel, then the program
build/NAME.map, .lbl, .dbgld65's map, VICE-style label file and debug file. Source-level debug information is omitted because cc65 embeds file timestamps in it.
build/layout.jsonEvery linked segment of every program
build/memory.jsonUsed and free bytes of each memory area of every program
build/manifest.jsonThe profile, the firmware baseline, tool versions and hashes of every input and output
build/asm/, build/obj/Staged assembler sources and objects

A separate project

python examples/starter/create.py DESTINATION makes a self-contained project: ordinary copies of the public headers, runtime sources, assembly backends, cfg/libtini.cfg, tools/disk.py, tools/setup_inputs.py, the ProDOS lock file and tools/DEPENDENCIES.md under runtime/, plus the starter's main.c, a build.py, a .gitignore, a README and SDK_INPUTS.json with every copied file's hash. It copies no objects, compilers, ProDOS image or links.

python runtime/tools/setup_inputs.py
python build.py --cc65-home D:/Repos/cc65 [--no-disk]

The project's build.py compiles every runtime source into its own build/libtini.lib, links main.c with runtime/cfg/libtini.cfg and writes build/APP.SYSTEM, APP.map, APP.lbl and, unless --no-disk, APP.po. It has no manifest: add sources and generated assets by editing the script.

Release archives

python tools/release.py --cc65-home D:/Repos/cc65 --verify-isolation

After both builds exist (build/ and build/private/, each with --test-target), this checks that no build input or output changed since, and with --verify-isolation copies the source files to a fresh folder under build/, rebuilds both variants there with only installed tools and the pinned ProDOS input, and requires identical outputs. It then writes dist/libtini-source.zip, the source without OS or ROM bytes, and dist/libtini-local-release.zip, which adds the built programs, disks and check records. The local release contains ProDOS inside its disks; check ProDOS's terms before sharing it.

Implemented in tools/build.py, tools/disk.py, examples/starter/create.py and tools/release.py.
