How libtini works

The ideas the rest of the reference relies on: two kinds of memory, who owns which part of the machine, the order of startup and shutdown, and the difference between a device clock and a display.

The target

A libtini program is a ProDOS SYS file that ProDOS loads at $2000 on an enhanced //e. The C code runs from main memory. The Super Hi-Res picture lives in auxiliary memory, bank 0, at $2000-$9FFF; the Appletini shows it when its fake SHR mode is on. RamWorks expansion banks, selected by writing a selector to $C073, hold the game's large data. The slot-4 card supplies sound, speech and a timer that does not depend on the CPU speed.

The library is written for cc65 2.19's C99 subset and its default calling convention: non-variadic functions are fastcall. All public types are fixed-width integers from stdint.h. Errors are uint8_t codes and handles are uint16_t. This is the first implementation's ABI, not a promise of a stable future one.

Near memory and banked resources

libtini keeps two kinds of memory apart.

Near memory

Near memory is ordinary C memory in main RAM: globals, the C stack, constants and the near arena. Every API call that takes a near pointer checks it against the regions the linker layout defines before it reads or writes anything:

  • The program's writable data and BSS, from the end of its saved OS state up to the layout's memory end.
  • The C software stack.
  • The near arena, where variables declared in the NEARBSS segment live.
  • For reads only, also the program's code and constants from $2000, and in the full-game layouts the constants copied to $0800-$1FFF.

A pointer outside these regions, such as the text screen, ProDOS's globals at $BF00 or I/O space, is rejected with TI_E_RANGE or TI_E_ARGUMENT. A zero length accepts any pointer, NULL included, and touches nothing. The checks catch mistakes; they do not track which object owns which bytes.

Banked resources

Large data lives in the RamWorks banks that the game grants with ti_init(first_bank, bank_count). Each granted bank contributes 48,640 bytes, its $0200-$BFFF range (TI_BANK_BYTES). The granted banks form one logical stream: an allocation is contiguous in that stream and may cross from one bank into the next.

A resource is a ti_handle plus byte offsets. There is no C pointer to banked bytes: the CPU sees a bank only for the length of one transfer burst, with interrupts masked, from a small trampoline in page one. Reads, writes, fills and copies move data between a resource and near memory, or between two resources, and check every handle and range before they start.

  • There are eight resource slots (TI_RESOURCE_SLOTS). A full-screen surface takes one, the active video session's screen backup another.
  • Allocation is first fit in the logical stream; capacity, fragmentation or a lack of free slots can make it fail with TI_E_NOMEM.
  • A handle encodes its slot and a generation. Freeing a resource invalidates every copy of its handle; using one afterwards returns TI_E_HANDLE.
  • Bank 0 is never a resource bank, and banks 1-126 are the ones the F1.3.2 baseline serves. Configured memory is never a flat 8 MB heap: a grant of all 126 banks gives 6,128,640 resource bytes.

Startup and shutdown

The project's startup code runs before main. It saves the zero page bytes cc65 uses, the page-one trampoline area, the entry processor status and the display switches it can read, masks interrupts, copies the full-game layout's low segments into place, clears BSS and the near arena, sets up the C stack and then enables interrupts again if they were enabled at entry.

A typical game then calls, in order:

  1. ti_init to grant banks.
  2. ti_gfx_surface_create and ti_gfx_begin for the screen.
  3. ti_audio_init for sound and the clock, and ti_steps_begin for fixed-rate updates.
  4. Its loop.
  5. ti_audio_shutdown, ti_gfx_end, ti_gfx_surface_free and ti_shutdown.

The last step is optional. Returning from main, or calling exit, runs ti_shutdown: it shuts down audio, ends the video session and restores the saved AUX0 screen, removes acceleration hooks and invalidates every resource. Startup then restores the saved machine state and calls ProDOS QUIT. Reset and power loss cannot run this cleanup.

If ProDOS refuses to remove the audio interrupt handler, shutdown returns TI_E_IO with the hardware silent and keeps the handler's code. Startup then refuses to quit, because ProDOS would call into unloaded memory: it shows CLEANUP ERROR. KEY RETRIES; CODE RETAINED on the text screen and retries on a key.

Everything runs in the foreground

Every libtini call is synchronous and none is reentrant. An interrupt or NMI handler must never call libtini, change memory mappings or the RamWorks selector, touch libtini's zero page or read granted banks. The library's own interrupt handler, the audio clock, is assembly that only counts ticks and acknowledges the timer. Long work gives the game a chance to keep sound going: a sprite scene calls its service function every fourth band, and a game can call ti_audio_update between its own drawing calls.

Errors

Every call that can fail returns a ti_error, where TI_OK is zero. Most games do not test every call: they wrap calls in ti_error_keep, which remembers the first failure, and check ti_error_first once a frame. Types and errors lists the codes.

ti_error_keep(ti_gfx_rect(&canvas, 0, 0, 320, 12, 1));
ti_error_keep(ti_gfx_text(&canvas, 8, 2, "SCORE", 13));
ti_error_keep(ti_gfx_present(&canvas, &bar, 0));
if (ti_error_first()) stop_game();

Device time and display edges

CPU delay loops cannot time a game that must run the same at 33 MHz and in TURBO. libtini counts time with the slot-4 card's VIA timer instead: ti_audio_init programs it for a nominal 100 ticks a second (TI_AUDIO_TICKS_PER_SECOND) and an interrupt handler counts them. ti_audio_ticks reads the count. The real rate depends on the card's clock; the via_hz setting accepts a calibrated value.

The //e's vertical blank flag at $C019 is a different thing: a level that libtini samples. ti_time_poll counts the blank-to-active edges it happens to see, which is a lower bound on the frames shown, not a clock and not proof that the Appletini presented a frame.

Some work stops the clock on purpose. File calls pause the audio driver while ProDOS owns the machine; the tick count does not advance, so the pause does not count as game time. A long interruption the driver does not know about leaves a gap: ti_audio_update and ti_steps_due report it instead of inventing time. Game loop and timing shows how a game handles both.

Putting pixels on the screen

libtini draws into software surfaces in banked memory, or composes a sprite scene in a near strip, and then copies the changed bytes to AUX bank 0 with ordinary CPU writes. A return from ti_gfx_present means those writes have finished. There is no second screen page and no atomic page swap: the Appletini samples the screen at its own frame boundary, so a large update can show half old and half new. Keep updates small: publish only the rectangles that changed. ti_gfx_present and ti_gfx_present_rows reject an update larger than their byte budget before writing, and an optional clock measures them.

The CPU-only and optional AMEM builds

The default build contains only CPU code paths. tools/build.py --private --build-dir build/private also links a transport for Appletini's private AMEM memory service. A program that calls ti_amem_enable in that build checks the exact controller and service first; large banked transfers may then use AMEM, with the same results as the CPU path. The screen is always written by the CPU. See Optional AMEM.
