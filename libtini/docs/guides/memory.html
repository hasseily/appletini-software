Memory and layouts

Where a program's code, data and stacks sit in the //e's 64 KiB, how to choose and adapt a linker layout, how to read the build's memory report, and what each part of the library costs.

The two shared layouts

Both produce a raw ProDOS SYS file loaded and entered at $2000, linked with cc65's none.lib and the project's startup. A manifest picks one with config.

In cfg/game.cfg, startup copies the low segments from the end of the loaded image into $0800-$1FFF once, before it clears BSS. The code that runs once at entry is in the ONCE segment, which that layout places where BSS will be, so clearing BSS reclaims it. Low memory remains read-only to the near-pointer checks.

A layout of your own

A game can link with its own copy of either file and take what it does not use from the library. STARFALL makes no file calls, so examples/starfall/starfall.cfg leaves _ti_file_buffer out and moves the end of WORK and of writable near memory, _ti_memory_end, from $AF00 to $B400: the guard page and the buffer become 1,280 bytes of game memory. A file call in that game would fail to link instead of letting ProDOS write over its variables. Keep the build's checks: it rejects any segment outside the regions a layout's symbols describe.

Reading the memory report

starfall memory: LOW $0800-$1FFF 88 free; IMAGE $2000-$BEFF 1032 free; WORK $A26C-$B3FF 1110 free; NEAR $B480-$B6FF 1 free
starter memory: MAIN $2000-$9FFF 12321 free; NEAR $A900-$AEFF 1532 free

Each entry is a linker memory area and the bytes still free in it. build/memory.json has the same figures with the used bytes, for every program. When a segment does not fit, the build stops with the shortfall:

starfall does not fit: segment BSS needs 50 more bytes in memory area WORK

IMAGE is the load image, which also carries the low segments until startup copies them, so its free bytes say how much more the SYS file can hold; WORK is where BSS lives once the program runs.

The near arena

Variables placed in the NEARBSS segment live in the layout's near arena, outside the program's main area. Startup zeroes them like BSS, the linker rejects more than the arena holds, and every near API accepts pointers into it. The library itself puts nothing there.

#pragma bss-name (push, "NEARBSS")
static uint8_t level[512];
static uint16_t palette[16];
#pragma bss-name (pop)

STARFALL keeps its 547-byte simulation state, star columns, animated palette and two text buffers there: 639 of the 640 bytes.

Placing code and data

cc65 puts code in CODE, constants in RODATA, initialized variables in DATA and the rest in BSS. Pragmas move a part of a file elsewhere:

/* Rarely used code into low memory, in the full-game layout. */
#pragma code-name (push, "LOWCODE")
static void title_option(void) { /* ... */ }
#pragma code-name (pop)

/* Keep this file's constants in main memory, where there is room. */
#pragma rodata-name (push, "CODE")
static const uint8_t table[64] = { /* ... */ };
#pragma rodata-name (pop)

Do not place code that runs after startup in ONCE, and keep OSSTATE to the startup code.

Auxiliary memory and banks

RangeOwner
Selector 0, all of itThe OS and the display; never a resource bank
Selector 0, $2000-$9FFFSHR pixels, scan-line bytes and palettes; all 32,768 bytes are saved by ti_gfx_begin
Selectors 1-126, $0000-$01FFReserved; never resource bytes
Granted selectors, $0200-$BFFF48,640 resource bytes per bank
Every selector, $C000-$FFFFI/O, ROM and language card; excluded

A resource crosses from $BFFF of one granted bank to $0200 of the next. Only the page-one trampoline runs while auxiliary reads are mapped, and main memory and selector 0 come back before C code or interrupts resume. A full grant of selectors 1-126 gives 6,128,640 resource bytes.

Saving memory and time with cc65

  • Foreground-only code that never recurses can use --static-locals in the manifest's cflags, as STARFALL does, which removes most C stack traffic.
  • Keep pools as parallel byte arrays (enemy_x[i], enemy_y[i]) rather than arrays of structures: the 65C02 indexes each with one absolute,Y operand.
  • Avoid 32-bit arithmetic in loops; the library's own checks moved to 16 bits for that reason.
  • The library favours memory over speed, because every game pays for its bytes. A game may spend its own memory where that buys speed.
